# ascal on Gowin — what we know, and how a Verilog port would go

Everything learned porting Temlib's `ascal.vhd` (MiSTer's scaler) to the
GW5AT-60 on a Tang Console 60K. Written so the next person — or the next
session — does not repeat any of it.

**Bottom line: ascal does not work on GowinSynthesis. Every input to the
failing logic is provably correct, the same RTL is correct under two other
synthesis paths, and ten separate hypotheses have been eliminated by
measurement.** A hand Verilog port is the last untried avenue; the fallback is
`docs/scaler_features.md`, which specifies the same capabilities on our own
scaler.

---

## 1. What ascal is

~3000 lines of portable VHDL. No vendor primitives. Used by every MiSTer core,
so it is heavily proven on Intel Cyclone V.

* **Five clock domains**: `i_` input video, `o_` output video, `avl_` Avalon
  memory, `poly_` coefficient load, `pal_` palette.
* **Avalon-MM burst master** to external memory. Frame(s) live in RAM.
* **Interpolators**: nearest, bilinear, sharp-bilinear, bicubic, polyphase
  (`mode[2:0]`), selectable at runtime; `MASK` decides which are *built*.
* **Triple buffering** via `mode[3]` — three base addresses from
  `buf_offset(buf, RAMBASE, RAMSIZE)`.
* **Input auto-detect**: measures the source window from `i_de`/`i_vs` edges.
  `iauto=0` + `himin/himax/vimin/vimax` pins it manually instead.
* **Arbitrary output timing** from `htotal/hsstart/hsend/hdisp` + `v*`.
* Note `i_hs` is genuinely **unused** — geometry comes from `i_de` and `i_vs`.

### Our integration (all working, all reusable)

| File | Role |
|---|---|
| `src/ascal/ascal.vhd` | upstream + minimal Gowin patches, regenerated by `tools/patch_ascal_gowin.py` |
| `src/ascal/ascal_gw.vhd` | wrapper: pins generics, exposes debug taps, converts `unsigned`/`natural` to `std_logic_vector` |
| `src/ascal/ascal_avl_ddr3.sv` | Avalon-MM burst master -> Gowin DDR3 app port |
| `ascal_test60k/` | bring-up rig: MCR test pattern -> ascal -> DDR3 -> DVI 720p |

**The bridge is proven good.** `src/ascal/avl_ddr3_memtest.sv` drives the same
bridge and controller with an address-derived payload (so a wrong *address*
fails as loudly as wrong *data*): **zero mismatches over thousands of passes**.

### Address units — the thing that will bite you

Three granularities are in play:
* ascal's `avl_address` is a **word** address, 1 word = `N_DW` bits = 16 bytes.
* the Gowin controller's `addr` counts **2-byte** DDR words.
* one Gowin command moves a full BL8 = 16 bytes.

So **`app_addr = avl_address * 8`**. Derived from gbatang's
`ddr3_framebuffer.v`, the only place this ratio is written down.

## 2. The fault

Source 512x480 upscaled into a 960-wide window inside 720p.
**Vertical is pixel-perfect. Horizontal renders the full source into a quarter
of the window, then blanks, then repeats.**

Measured off a capture card:

```
window hmin=160 hmax=1119 (960 px):  content 160..399 (240 px) then repeat at 672..911
window hmin=0   hmax=1279 (1280 px): content 0..319  (320 px) then repeats at 512, 1024
```

Content width is always `512 x window / 4`. **The repeat period is 512 output
pixels — equal to the SOURCE width — and it does not change when the output
window changes.** That invariance is the strangest single fact we have.

### Confirmed CORRECT on hardware, by on-chip taps read over UART

| signal | hardware | meaning |
|---|---|---|
| `i_himax` / `i_vdmax` | 511 / 479 | auto-detect works |
| `i_hsize` | 512 | input window |
| `o_ihsize` | 512 | input width, after the i_clk->o_clk `<ASYNC>` crossing |
| `o_hsize` | 960 | output window |
| `o_hmax` | 1119 | |
| `i_hdown` | 0 | not in downscale mode |
| `o_hburst` | 1 | bursts per line |
| `{o_copylev,o_hbcpt}` | 0x04 | copy queue not starved (matches sim exactly) |
| `o_ihsizem` | ~510 | **line-end threshold is correct** |
| `o_off(0)` / `o_pshift` | 0 / 15 | see the divergence note below |

### Eliminated by experiment — do not repeat any of these

Each was rebuilt and re-measured on hardware; **all produced byte-identical
wrong output**:

* `OHRES` 2048 vs 2304 · `FRAC` 4 vs 8 · `N_BURST` 256 vs 2048
* interpolator mode 0 (nearest) vs 2 (sharp bilinear) — mode-independent
* auto-detect vs hard-baked input window (`iauto=0`)
* **four** different formulations of the carry arithmetic:
  original modular form; explicit-width `unsigned` expression; `unsigned`
  signals with wraparound-as-MOD; plain `IF acc >= 2*o_hsize` compare
* every register pipeline forced out of RAM (`syn_keep`/`syn_preserve`;
  SSRAM fell 21 -> 15, ~450 registers moved, zero behavioural change)
* Avalon clock phase 0 vs 90 degrees (in sim)
* the Avalon bridge and the DDR3 path (hardware memtest, zero errors)

**The netlists genuinely differ** between patched and unpatched builds
(md5 `b27a7803…` vs `28c95229…`), so the edits *do* reach silicon. Two
materially different implementations of the carry produce identical wrong
output — which argues the carry arithmetic is not the fault.

### Correct under two other synthesis paths

1. **GHDL behavioural** — renders pixel-exact.
2. **GHDL's own synthesis engine, simulated gate-level under verilator** —
   `ghdl synth --out=verilog` then verilator: bars at
   81-158, 161-238, 241-318, 321-398, 401-478, 481-558, 561-638,
   78-80 px each (expected 640/8 = 80). **Correct.**

This is the gate-level check Gowin's `pragma protect`-encrypted `.vg` denies us.

## 3. Known sim-vs-hardware divergences (IMPORTANT)

`sim/mk_ascal_sim.py` guards three `natural` underflows that abort GHDL. The
simulated RTL is therefore **not** byte-identical to the synthesized RTL:

| line | expression | hardware | our sim |
|---|---|---|---|
| ~2247 | `o_pshift <= o_off(0) - 1` | wraps to **15** when `o_off(0)`=0 (**confirmed by tap**) | forced to 0 |
| ~2274 | `o_pshift <= o_pshift - 1` | wraps at 0 | held at 0 |
| ~2250 | `o_ihsizem <= o_ihsize + o_off(0) - 2` | wraps if sum < 2 | forced to 0 |

Believed inert — `sSHIFT` is only entered when `o_off(0) > 0`, and
`o_ihsize`=512 in steady state — but **not proven inert**. Any claim that
"simulation proves the RTL is fine" carries this asterisk.

### A structural detail worth carrying into any port

`o_hacpt` (source pixels consumed) is advanced in **two** places:

```vhdl
WHEN sSHIFT =>  o_hacpt <= o_hacpt + 1;   -- every sSHIFT cycle
WHEN sCOPY  =>  IF hcarry_v THEN o_hacpt <= o_hacpt + 1; END IF;
```

The `sSHIFT` path is independent of the carry logic. That is why rewriting the
carry four ways changed nothing, and it is the first thing to get right in a
port.

## 4. Four separate GowinSynthesis defects hit by this one file

Written up for submission in `docs/gowin_bug_report.md`; packaged reproducer
in `gowin_bug_repro/` (`tools/make_gowin_repro.py` regenerates it).

| # | Defect | Status |
|---|---|---|
| 0 | **SIGFPE crash** in "Running inference", V1.9.12.03 only | regression; 1.9.11.03 builds the same sources |
| 1 | **Silent horizontal miscompile** | the subject of this document |
| 2 | `PA2122` — inferred BSRAM shift register given an unsupported `WRITE_MODE` | worked around with `syn_srlstyle "registers"` |
| 3 | `CK3001` — invalid DSP `CASI` cascade on the GHDL-generated Verilog | blocks that workaround on both versions |
| 4 | `ramstyle` / `syn_ramstyle` / `syn_multstyle` silently ignored | `syn_keep`/`syn_preserve` *are* honoured |

Also: **stay on V1.9.11.03.** V1.9.12.03 cannot build ascal at all.

## 5. How a hand Verilog port would go

The mechanical route is already done and blocked: `ghdl synth --out=verilog`
gives a *correct* Verilog ascal (verilator-proven) that Gowin rejects with
CK3001, and reducing `MASK` does not dodge it (160 wide multipliers -> 108,
not 0). A **hand** port is different: idiomatic RTL that Gowin infers
normally, rather than a flattened netlist.

### Type mapping

| VHDL | Verilog |
|---|---|
| `type_pix` record (r,g,b : unsigned(7:0)) | packed `[23:0]`, or a `struct packed` |
| `arr_pix(0 TO 3)` | packed `[95:0]`, sliced by index |
| `arr_pixq(2 TO 8)` | 7 discrete regs — **do not** use an array; Gowin infers RAM from register arrays and then mis-configures it (defect 2) |
| `natural RANGE 0 TO N` | `reg [$clog2(N+1)-1:0]`, wraparound explicit |
| `MOD 2**k` | bit mask / truncation |
| functions returning records | functions returning packed vectors |

### Order of work — each stage independently testable

1. **Skeleton + ports.** Match `ascal_gw.vhd`'s interface exactly so it drops
   into the existing rig and testbenches unchanged.
2. **Input capture** (`i_` domain): `i_de`/`i_vs` edge detect, `i_hsize`/
   `i_vsize` measurement, line buffering, burst writes to Avalon.
3. **Avalon master FSM.** Semantics, verified against ascal's `Avaloir`:
   *write* holds `avl_write` for the whole burst, address presented once, one
   word per non-waitrequest cycle, `BLEN` times; *read* holds `avl_read` until
   one non-waitrequest cycle, then `BLEN` words arrive via `readdatavalid`.
4. **Output raster** from the timing parameters — `o_hs/o_vs/o_de` are
   ACTIVE HIGH.
5. **Line fetch + `sWAIT`/`sSHIFT`/`sCOPY` FSM.** Get the *two* `o_hacpt`
   increments right (see §3).
6. **Bresenham** — plain `if (acc >= 2*o_hsize)`, no modular sign trick.
7. **Interpolators**, cheapest first: nearest -> bilinear -> sharp bilinear.
   Bicubic/polyphase last; they are where all the DSPs go and the likely
   CK3001 trigger.
8. **Triple buffering** — three base addresses, swap at vsync.

### Test strategy — already built, reuse it

* `sim/vsynth/` runs a **verilator** harness against the real
  `mcr_testpattern.sv`, real `ascal_avl_ddr3.sv` and a Gowin-style DDR3 model.
  **~2 seconds per run** (iverilog took over an hour and never finished; GHDL
  behavioural takes ~30 min). Use this for every stage.
* `tools/ascal_sim_check.py` measures the output into colour-bar runs; the
  known-good reference is bars of 78-80 px spanning the window.
* Watch the frame rate: a 640x480 output raster free-runs at ~177 Hz against a
  60 Hz source, so **dump a late frame (24+)** or the framebuffer is not yet
  filled and everything reads black.
* Build for hardware with `tools/gw_build.sh ascal_test60k`, flash, and
  capture with the MiraBox on `/dev/video4`. **SRAM loads fail silently ~1/3
  of the time — always confirm via the UART beacon signature before trusting
  a result.**

### Risks, stated plainly

* ~3000 dense lines. Every translation error looks exactly like the bug.
* It may end where we are now: the fault might be a Gowin inference issue that
  idiomatic Verilog reproduces.
* Bicubic/polyphase may re-trigger CK3001 regardless of language.
* **Suggested tripwire:** port through stage 6 (nearest-neighbour only) and
  test on hardware *before* writing any interpolator. If nearest-only renders
  correctly on Gowin, the port is viable and worth finishing. If it shows the
  same 4x/512 signature, stop — and fall back to `docs/scaler_features.md`.

## 6. The Verilog port (`src/video/ascal_v.sv`) — bring-up log

Nearest-neighbour only, 16 bits/pixel so exactly 8 pixels fill one 128-bit
word. Builds clean on Gowin: ~4.3k registers, 28/118 BSRAM, no undeclared
symbols, no setup/hold violations, only the accepted `gowin_pll_hdmi` PA1019.
**It renders correct colour bars on hardware — which ascal itself never did.**

### Bugs found, in the order they bit

| # | Symptom | Cause | Fix |
|---|---|---|---|
| 1 | capture card would not lock | vsync asserted on only 2 lines (`ocy==VSSTART \|\| ocy==VSEND-1`) | continuous pulse `>=VSSTART && <VSEND` |
| 2 | one source line for the whole frame | fetch gated on `ocx==0 && sy!=sy_d`, but `sy` updates AT `ocx==0`, so the compare is always false there | compare against the line actually fetched |
| 3 | wrong addresses entirely | reader used `MAX_WIDTH/PPW` (128) as stride; the writer emits `ceil(width/PPW)` (64) | derive `line_words` from the DETECTED width |
| 4 | — | write burst started with one word in the FIFO and wrote 7 garbage words | start a burst only when a whole burst is buffered |
| 5 | **colourful horizontal streaks** | **one line buffer: the fetch for line L filled the RAM being scanned. `o_de` starts at `ocx==0`, so the only slack was the 160 px pillarbox** | **ping-pong halves + prefetch a full output line ahead** |
| 6 | frame = one line repeated | swap gated on a read-completion toggle; if it never fires `swap_req` latches high and the fetch gate never reopens — deadlock | swap unconditionally; busy check is diagnostics only |

### The methodology point — write the checker before trusting the sim

Bug 5 passed simulation for several iterations. Two reasons, both worth
remembering:

1. **The checker was too weak.** It measured colour-bar widths on one or two
   rows. An under-run line buffer returns *stale* data, and on a repetitive
   test pattern stale data still measures as plausible bars.
   `tools/scaler_check.py` now validates the whole frame and fails loudly.
2. **The DDR3 model was too kind.** Fixed 12-cycle latency and a 3-in-16 stall
   let the reader win a race it loses on real silicon. `sim/vsynth/ddr3_model.v`
   now models refresh-like stalls (`STALL` parameter).

**Even so, neither model configuration reproduced bug 5.** Arithmetic says why:
64-word burst + 12 cycles latency + 40-cycle stall = 116 cycles, still inside
the 160-cycle pillarbox. Cranking the stall to 250 starves the *write* path too
and the frame just goes black, so that test proves nothing either.

**What actually settled it was on-chip measurement, not simulation** — the same
lesson as the ascal investigation itself. `dbg_underrun` is reported in the UART
beacon (`L` field, low nibble, saturating) and read `F` immediately. Report it
**per frame**, not free-running: a free-running counter pegs on startup
transients and then tells you nothing about steady state.

The `L` field's high nibble is a per-build marker. **Never trust a hardware
result without it** — SRAM loads fail silently about a third of the time.
